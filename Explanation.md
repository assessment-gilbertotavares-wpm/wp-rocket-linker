# WP Rocket Linker — Explanation

## Problem Description

We needed to track, on each homepage visit, which links were visible **above the fold** (i.e., without scrolling), and keep these records for up to **seven days**. This helps site owners understand which links get the most attention right after page load.

---

## Solution Overview

### Front-end

* A JavaScript script is loaded **only on the homepage**.
* The script identifies all `<a>` elements, filters those that appear **above the fold** and collects:

  * URL
  * Link text
  * Screen dimensions
  * Timestamp
* The data is sent to the backend via a **custom REST API endpoint**.

### Back-end

* **BerlinDB** is used to store data in three relational tables:

  * `wrl_entries`: one row per visit, storing date (GMT and local) and screen size.
  * `wrl_links`: unique links (based on URL + text).
  * `wrl_link_relationships`: links entries to multiple links per visit.
* A custom REST endpoint at `/wp-rocket-linker/v1/entry`:

  1. Requires an authorization token generated by the backend.
  2. Verifies the token via the `X-WP-Rocket-Linker-Token` HTTP header.
  3. Stores `entry_date_gmt` and converts it to local WordPress time (`entry_date`).

### Admin Panel

* A new admin page using `WP_List_Table` displays:

  * Entry date
  * Screen dimensions
  * Visible links
* Includes pagination, sortable columns, and contextual help.

### Cleanup

* A scheduled `wp_cron` task removes entries **older than 7 days**.

---

## Technical Details and Justification

### REST API Permissions

* Instead of using `__return_true`, a secure public token was introduced.

* This token is passed to JavaScript and sent in the request headers, preventing unauthorized external calls.

### Date Handling

* `entry_date_gmt` is stored in UTC for consistency.
* `get_date_from_gmt()` is used to convert it to local time when displaying in the admin interface.
* This ensures consistency across time zones and server configurations.

### Use of BerlinDB

* A relational model allows flexible queries and avoids JSON duplication.
* Suggested updates to the Engineering Handbook:

  * Use a more declarative format for `schema->columns`.
  * Define `item_name` as a unique string (not a Row class reference).
  * Ensure `item_shape` refers to the Row class itself, not just an array of columns.

### Architecture & Code Quality

* The code follows **PSR-4 autoloading** and clean **object-oriented design**.
* Organized by namespaces:

  * `Admin`
  * `Database`
  * `REST`
  * `Frontend`

---

## How It Meets the User Story

* Admins can view, in chronological order, all homepage visits from the last seven days.
* Each record lists the links visible above the fold at page load.
* The interface is accessible via the **“Linker Entries”** menu.
* The endpoint is secured and time zones are handled consistently.

>

>   * Treat `item_shape` as a class name (derived from `Row`), rather than an array of columns.
>   * Define `item_name` as a `string`, also represented by a class derived from `Row`.
>
>   > These handbook recommendation were developed considering the `berlindb/core` package v2.x and **have not** been tested on the `wp-media/berlindb-core` fork.
